Pattern

Forms

Wayfold asks members for a sign-in, a sign-up, their settings and a car listing, and asks providers for a business profile. Every form is one column in a card, checks on submit, keeps what was typed, names exactly what to fix, and ends with one primary button that says what it does.

Overview

A Wayfold form is a form.card.stack holding div.field rows (label, control, then help or error), an optional alert at the top, and a single primary submit. Forms validate on submit, never on every keystroke. A failed submit puts a danger alert first and marks each field with aria-invalid and its own message. Success either swaps the form for a confirmation card (sign-up, vehicle listing, provider profile) or shows a success alert above the kept form (settings).

Dialog forms (add a car, ask an expert, contact a dealer, recommend) follow the same rules inside .dialog__body; see Dialogs and overlays.

Structure

Order inside the card: alert (only after a submit), fields in the order a person thinks of them, supporting media, then the primary button. Optional fields say "(optional)" in the label; required fields carry required and no asterisk.

Responsive behaviour

  • Forms are always one column. .auth and .container--narrow cap the line length; below SM the card fills the width with the page gutter.
  • The primary button is full width below SM and its natural width above.
  • Selects and inputs keep a 16px font size so phones do not zoom on focus.
  • Vehicle photo previews scale to the card width and keep their aspect ratio.

Accessibility

  • Every control has a visible <label for>; help and errors join through aria-describedby.
  • After a failed submit, move focus to the alert (or the first invalid field) so the error is announced (WCAG 3.3.1, 4.1.3).
  • Use autocomplete on email, name and password fields and allow paste and password managers (WCAG 1.3.5, 3.3.8).
  • Disabled submits carry aria-busy="true" and a changed label; never disable a submit only because a field is empty.
  • Errors pair the danger colour with the warning glyph and text, never colour alone (WCAG 1.4.1).

Content

  • Labels are nouns in sentence case: "Display name", "Price (CAD)", "Mileage (km)", "GTA municipality".
  • Errors say what to enter: "Enter a valid email", "Use at least 12 characters". Add an example when there is a format ("like 2015").
  • Alert titles are short: "Check these fields", "Check the listing", "Something went wrong", "Too many attempts", "Saved".
  • Buttons are verb plus object: "Sign in", "Create account", "Save settings", "Publish listing", "Save business profile". Busy labels use the -ing form with an ellipsis: "Signing in…".
  • Church fields are always optional and say who can see them: "Your church is never visible to signed-out visitors."

Do and don't

Sources

  • Sign in: default, loading, invalid, submitting, error, locked
  • Sign up: default, invalid, submitting, error, success
  • Settings: default, invalid, submitting, success
  • Vehicle editor: default, dealer, invalid, success
  • Provider editor: default, invalid, submitting, success

Drift found in the mocks:

  • vehicle-editor/invalid marks Year "2015" invalid with "Enter a year". The system marks only wrong values and gives a format example.
  • Optional fields are written inline as "Home church (optional)" in settings instead of the .optional span. Use the span.
  • Password rule "12 characters" appears only as an error on sign-in/sign-up. Show it as help on sign-up; on sign-in report only "Enter your password".
  • provider-editor shows the financing credential field to every category. Show it only for Financing.
  • Inputs in the mocks lack autocomplete; the system adds it for email, name and passwords.
